Why this works

Amber keeps all state in memory (Clock at src/main.rs:216, selected at main.rs:1254). Nothing is on disk. A single writer means there are no merge rules. Followers hold no authority: they send a command, the primary applies it, then broadcasts the new snapshot.

4Wire into main loopdone

Every key that changes shared state pushes a Request onto pending. One place decides: a follower sends it, anyone else acts on it.

+ let mut pending: Vec<Request>;   let mut task_title: Option<String>;   let mut link: Option<Link>;
+ top of loop: link.poll()  →  Request → pending · State/Gradient/Notice → apply (followers only)
+ for request in pending { follower ? link.request(r) : match r { TogglePause, ResetCycle, NewLyric, SelectTask, GoHome } }
~ Space      toggle_pause(...)        →  pending.push(Request::TogglePause)
~ r (Task)   clock.reset(...)         →  pending.push(Request::ResetCycle)
~ r (Home)   request_moment_gradient  →  pending.push(Request::NewLyric)
~ Enter      selected = Some(chosen)  →  pending.push(Request::SelectTask(chosen))
~ Enter      going-home block         →  pending.push(Request::GoHome)   // block moved into the dispatch
~ schedule.due(...)   →  a follower logs and does nothing
~ scheduled start and resume  →  + link.notice(text)
~ clock.advance(now)   →  skipped on a follower; the phase comes from the primary, and its chime plays on the change
~ ambient moment      →  a follower does not ask Jev for a first gradient
~ after generator result or cached hit  →  link.publish_gradient(...)
~ before drawing      →  primary: link.publish(shared_state(...), now)
- Not synced after all: the moment text. Followers still fetch weather, so one can take over.
5Failover and lifecycledone

Connection lost or 5 s of silence: the follower waits 500 ms + id % 1000, then probes again. Nobody answers: it becomes primary and resumes from the last state and gradient it saw.

+ manage() in src/sync/mod.rs   probe → follower::run or primary::run → on exit, wait and probe again
+ primary: beacon every 2 s; a beacon from another primary that outranks it sets `demoted`
+ follower: drops requests queued before it connected
+ Who stays primary when two meet, in order:
+   1. later last_interaction_ms   // any person on any machine of the group; starts at 0; stamped by the primary's clock
+   2. higher priority             // primary has N, each follower N-1; a follower that takes over keeps its own number
+   3. lower id                    // random 64-bit, made at start
+ Interaction: Link::interacted() on key actions (Space, r, Enter, opening the task menu) and when a follower's request is applied
+ Standing travels in the welcome, after each interaction, and in every beacon; a follower keeps (time, priority - 1) in Memory
+ Scheduled work starting does not count as an interaction
+ A returning old primary wins a tie, so the group adopts its state. Someone using the group in the gap beats it.
  Role changes show as a notice: "Sync: this machine is now the Primary"
