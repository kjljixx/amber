Sync plan

Amber sync security

Outsiders on the LAN can neither read nor control Amber. Everyone who holds the key is trusted. Built: all four stages.

1key: 32 random bytes, made by --sync-keygen
1new dependency: snow 0.10
0new message types

Why a random key, not a typed onelimit of Noise

Noise uses the key as a raw secret. It does not protect a weak one. The first message already holds a check value made from the key. Anyone who records one handshake can test guesses on their own machine. A typed word falls in seconds. 32 random bytes cannot be guessed. A typed passphrase would need a second library (spake2) and more code.

Stages

1Key and --sync-keygendone

Add snow. Add Key and hex parsing. Settings holds a Key. Add the flag.

Done when: amber --sync-keygen prints 64 hex characters, and a malformed SYNC_SECRET stops Amber with a clear message. A missing one leaves sync off.

2Channeldone

initiate, respond, seal, open. Tested alone over a loopback socket, before any other code uses them.

Done when: the tests for the channel pass. If TransportState cannot go behind a Mutex across threads, use StatelessTransportState with one counter for each direction.

3Wire it indone

Change serve and follower::run. Remove the secret from Hello. Update the existing sync tests to use a key.

Done when: every old sync test passes with keys, the wrong-key test sees the notice, and the wire test finds no readable text.

4Docs and a real rundone

README, .env.example, sync-plan.html. Run Windows and Mac with one key, then with a wrong key. Read sync.log on both.

Done when: logs show the handshake, no key, and a refused wrong-key attempt.
